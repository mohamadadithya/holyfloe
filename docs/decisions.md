## Scope and positioning

- D-001 SETTLED: The engine generates real framework components for React, Vue 3 and Svelte 5, not only type augmentations. Types-only output is a secondary mode.
- D-002 SETTLED: Input contract is Custom Elements Manifest schema 2.1.0. The Rust engine does not parse Lit source until M4.
- D-003 SETTLED: Do not depend on `@chialab/plasma` (archived Jan 2026) or `@lit-labs/gen-wrapper-*` (pre-1.0 labs). Study only.
- D-004 SETTLED: wc-toolkit packages are the reference for output shape. Port shapes, do not copy code.
- D-005 SETTLED: Differentiators are one IR for three frameworks, two-way binding as an IR concept, native speed with incremental watch, and exact types without a checker.

## Architecture

- D-010 SETTLED: Pure core. Emitters are `fn(&Ir, &Config) -> Vec<OutputFile>`.
- D-011 SETTLED: One IR feeds all emitters. Emitters never read CEM directly.
- D-012 SETTLED: Framework files are rendered from minijinja templates. No AST printer for `.svelte` or `.vue`.
- D-013 SETTLED: Types are never resolved. Emit `import type` plus indexed access (`El['prop']`). No TypeScript checker, no tsgo, in the core.
- D-014 SETTLED: Inheritance and mixins are flattened in an IR pass over own + dependency manifests. Cycles are an error.
- D-015 SETTLED: Event names keep the raw DOM name and a derived prop name. Both live in the IR.
- D-016 SETTLED: Prop kind (Boolean, Primitive, Complex) is classified in the IR and drives SSR attribute vs client property handling.

## Per-framework

- D-020 SETTLED: React has two modes: `wrapper` (React 18 and 19, default) and `types` (React 19 only).
- D-021 SETTLED: React wrappers emit `'use client'` by default.
- D-022 SETTLED: React wrappers pass Primitive and Boolean props as attributes (SSR-correct) and set Complex props as properties in a layout effect.
- D-023 SETTLED: Vue output is `defineComponent` render-function wrappers in `.ts`, not `.vue` SFCs.
- D-024 SETTLED: Svelte output is real `.svelte` files using runes. `peerDependencies: svelte ^5`.
- D-025 SETTLED: Svelte named slots are snippet props rendered inside a `display: contents` wrapper carrying the `slot` attribute.
- D-026 SETTLED (syntax in D-062): Two-way binding is a first-class IR concept (`TwoWayBinding`). Convention: JSDoc tag `@model <prop> <event>` plus config override.
- D-027 SETTLED: Scoped slots (data-passing) cannot cross shadow DOM. Type them as `() => VNode[]` only. Document it.

## Libraries

- D-030 SETTLED: CEM input generated by `@custom-elements-manifest/analyzer` with `--litelement`. `@wc-toolkit/cem-generator` is watched, not used (prototype).
- D-031 SETTLED: Rust CEM types generated once by `typify` from the schema and checked in. Not regenerated in `build.rs`.
- D-032 SETTLED: Templates use `minijinja` 3.0.1 with the `serde` feature on. In 3.x `Value::from_serialize` is gone: pass serde data as `Serde(&x)` (`minijinja::value::Serde`), e.g. `context!(c => Serde(&c))`. Proven by the M0 spike test in `holyfloe-emit-core` (removed in M1 step 3; the emitters now exercise it).
- D-033 SETTLED: Snapshot tests use `insta` + `cargo-insta`.
- D-034 SETTLED: CLI uses `clap`. Watch mode uses `notify` + `notify-debouncer-full`. In the bundler plugin, the bundler's watcher is used instead.
- D-035 SETTLED: Node distribution via `napi-rs` v3 with native binaries plus a `wasm32-wasip1-threads` fallback. Bundler integration via `unplugin`.
- D-036 SETTLED: Own Lit parser (M4) uses `oxc_parser`, `oxc_ast`, `oxc_semantic`, `oxc_resolver`. Optional. Analyzer stays as `--input cem` fallback.
- D-037 SETTLED: Formatting is done by the user's formatter from the JS layer (`--format`). No Rust formatting crate in the core.

- D-074 SETTLED (fx-button review, Chromium dev and prod plus Vite SSR, 2026-10-18): wrapper mechanics chosen from the installed Vue 3.5.44 and Svelte 5.57.2 sources and proven in the browser. Vue: listeners are case-exact `'on:<dom_name>'` vnode keys (attached at element creation, so `fx-ready` from Lit's first update arrives); `setup()` returns `element` and method forwarders so they are typed instance members (no `expose()`); vnode props pass through `defined()`, without which an unset `variant` became `''` instead of the default. - D-085 SETTLED (M3): the on-disk pipeline (read manifest, config and dependency manifests, build, emit, write) is the lib target of `holyfloe-cli`, shared by the binary and `holyfloe-napi`; no new crate, and disk access stays in cli/napi/fs. - D-086 SETTLED (M3): watch mode (`holyfloe generate --watch`, `watch()` in Node) re-runs `generate` when the manifest or config changes. Tests cover both, compares canonical paths (macOS reports `/private/var/...`), ignores access events (`generate` reads the manifest itself), debounces 100 ms, and starts before the first run so no change is missed. A failed run is printed and the watch goes on. In Node, a `Watcher` that is no longer referenced keeps watching (and the process alive) until `close()`, as `fs.watch` does; `close()` aborts the callback, so queued runs never reach JS. Dependency manifests are not watched. The analyzer is not run: users keep `cem analyze --watch` running.

- D-089 SETTLED (M4): `holyfloe-lit` reads Lit source with oxc (`oxc_parser`, `oxc_ast`, `oxc_ast_visit`, `oxc_resolver`; no `oxc_semantic`, nothing needs scopes) and returns a manifest as `serde_json::Value`, not IR. Callers parse it with `holyfloe_cem::parse` (so D-049's strict element check applies) and build the IR as for analyzer output: discovery, module and `exports` resolution, flatten across files and packages and every pass are shared, and parity compares two `Library` values. Relative imports are written verbatim (the IR resolves them, D-050); bare specifiers go through `oxc_resolver` (`.js` to `.ts`, tsconfig `paths`), and a hit inside this package (no other named `package.json` in between, not in `node_modules`) becomes a module path and is extracted too, so a base class outside the scanned files is still found. Anything else is a `package` reference, looked up in dependency manifests (D-069).
- D-090 SETTLED (M4): what the extractor reads, matching the analyzer where it decides. Tags: `@customElement`, `customElements.define` anywhere in a module (also through `window.`/`globalThis.`), JSDoc `@tag`/`@tagname`; a defined tag beats `@tag`, as in the analyzer's tag linking. Members: public instance fields, `accessor`s, getters (read-only without a setter) and methods; skipped are `private`/`protected`/`#`, statics (except `formAssociated`, D-065), `@internal`, `@state`/`@query*` fields and the analyzer's Lit deny list (`render`, `update`, `updated`, `firstUpdated`, `willUpdate`, `shouldUpdate`, `performUpdate`, `scheduleUpdate`, `requestUpdate`, `createRenderRoot`, `styles`, `properties`). `static properties` (field or getter) with defaults from `this.x = …` in the constructor; `state: true` entries skipped. Type text, first match: the TS annotation verbatim (`| undefined` appended when optional, as the analyzer prints it), JSDoc `@type`, the initializer literal (`string`, `number`, `boolean`, `bigint`), `@property({type})`; else none, which is Complex. Events: `@fires`/`@event` first, then `dispatchEvent(new X<T>('name'))` in the class body; a documented event without a type takes the dispatch's. Detail type references come from imports and module-local type aliases and interfaces.
- D-091 SETTLED (M4): without an `attribute` option, the attribute is the property name lowercased, which is what Lit observes. The analyzer writes the property name (`ringColor`). Both work, because the HTML parser and `setAttribute` on HTML elements lowercase attribute names, but the lowercased name is what the element really has.
- D-092 SETTLED (M4): Lit input in the CLI: `holyfloe generate --lit <dir>`, exclusive with `--cem` (a clap group requires one). `<dir>` is scanned recursively for `.ts .tsx .mts .js .mjs .jsx`, skipping declarations, `node_modules`, dot-directories and `--out`, so wrappers written inside the source tree are never read as sources. The package is the nearest named `package.json` at or above `<dir>`. `--watch` watches `<dir>` recursively and re-runs only for such source files. The library's `Options.input` is `Input::{Cem, Lit}`; cargo feature `lit` (default) pulls in `holyfloe-lit`, and the binary requires feature `watch`.
- D-093 SETTLED (M4): Lit input in Node and bundlers. `@holyfloe/core` `generate()`/`watch()` take `lit` (a directory) or `cem`, exactly one (`InvalidArg` otherwise); napi feature `lit` is on in the native and the wasm build (oxc compiles for `wasm32-wasip1-threads`; the wasm build is `--no-default-features --features lit`). `@holyfloe/unplugin` takes the same option and regenerates when a source file under it changes, filtered like the CLI (D-092): editing a component's `.ts` rewrites only the affected wrapper and Vite sends a `js-update` for it, with no analyzer step (test `lit:` in `packages/unplugin`).
